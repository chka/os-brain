Help

Something wrong?
Tell us.

If something is broken, open an issue on GitHub. If something just is not doing what you expected, the checks further down usually answer it first.

Reporting a problem

Bugs, wrong output and refusals that make no sense go to github.com/chka/os-brain/issues. os-brain has no reporting command and sends nothing anywhere by itself, so an issue is the only way we hear about it.

A report we can act on has these in it:

  1. The version. Paste the output of os-brain version, which names the build and the schema version.
  2. Your system. The operating system and which agent ran the command, if one did.
  3. What you ran. The exact command with its flags, or the MCP tool call.
  4. What you expected and what happened instead. Paste the output as it was, refusal messages included. Every refusal names what it protects, which tells us most of what we need.
  5. The state, if it matters. The output of os-brain doctor and os-brain stats.
$ os-brain version
os-brain 26110501 (schema v16)
$ os-brain stats
memories=6 (pinned 0, superseded 1) [A3 B2 C1] scopes=3 events=3 leads=0
db=/home/you/src/orchard/brain/brain.db
Issues are public. Your memories are stored in cleartext and the output of recall, brief or export may carry them. Cut anything private before you paste: hostnames, paths, project names, the text of memories. Never attach a brain.db or an export.

If you found a security problem, do not describe it in a public issue. Open one that says only that you have a security report and how to reach you. We will arrange a private channel.

An agent running os-brain is told the same thing by one of the default axioms: when os-brain behaves wrongly, tell the user what was run, what was expected and what happened, so they can report it here. It does not work around the problem in silence.

When it is not doing what you expected

Most surprises are the brain refusing to guess. These four commands answer most of them: which file it opened, which project it thinks this is, which build you have and whether the brain is healthy.

$ os-brain env      # paths, the project name, git, the clock
$ os-brain stats    # counts, then the database path on line two
$ os-brain doctor   # is the brain in good shape
$ os-brain version

The session started without the brief

Run os-brain wakeup in the project.

  • It prints the brief: the hooks are not set up. Run os-brain init again. It replaces the hooks rather than adding more.
  • It says there is no brain here: you are outside the project. Run it from inside, or set OS_BRAIN_HOME to the brain directory.
  • Command not found: the binary is not on this PATH. Your agent's PATH is often not the same as yours.
  • It prints the brief yet the session still shows nothing: some agents run hooks only for new sessions. Open a new one rather than resuming.

A search finds nothing

  • Read the first line of the result. When no memory holds most of your words, it says the match is loose and that the results are leads, not answers.
  • Use fewer words, or the words a memory's title would use.
  • Search a wider scope. A search in deploy:prod sees deploy and everything global. It never sees a scope filed beside it.
  • If you can open a memory by its id but a search never finds it, os-brain reindex rebuilds the search index.

It shows no memories but you know there are some

It opened a different file. os-brain stats prints which one on its second line. A project with its own file and the shared store cannot see each other's memories.

It refused to do something

Read the message. Every refusal says what it is protecting and how to get past it when you really mean it: a memory that already covers the same thing, a pinned rule, a delete that would bring back facts you corrected, text that looks like a password. Do not work around a refusal you do not understand. That is how memories get lost.

Something looks damaged

os-brain doctor checks the brain and says what is wrong. os-brain doctor --fix repairs what it can and names the rest. Do not fix the database by hand. wakeup takes a safety copy at most once a day when the store has changed: os-brain backup --list --verify lists the copies and checks each one, os-brain backup --restore <file> shows what would change and adding --apply puts one back.

The full list is on the troubleshooting page. Still stuck? Tell us, with the command you ran and what it printed.
